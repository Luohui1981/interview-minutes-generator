# 访谈纪要详细流程

本文件用于超长逐字稿、复杂追问、多位受访者、内容覆盖矩阵、断点恢复和完整性复核。

## 1. 元信息与输出目录

建议目录：

```text
访谈纪要/{受访单位简称}_{主要受访者姓名}_{YYYYMMDD}/
```

要求：

- 日期统一为 `YYYYMMDD`
- 清理 Windows 非法文件名字符
- 多位受访者使用主要受访者命名目录，正文列出全部人员
- 缺失信息确实影响结果时再询问；用户无法提供时写“待确认”

## 2. 《访谈实录》整理

目标是保留全部有效信息，同时提升可读性。

- 删除无实质信息的语气词、应和句和重复尾音
- 保留观点、推理、数据、案例、类比、条件、否定、犹豫和观点变化
- 追问打断回答时，先恢复上一回答的完整性，再记录追问
- 不把不同主题硬性合并
- 不把原判断改写得更强或更弱
- 说话人不清晰时结合上下文判断；仍不确定则保留风险标记
- ASR 中无法确认的专名、数字或单位标记“待核听”，不得猜测

逐字稿超过约500行时分段整理；合并为完整实录并落盘后，后续阶段只读取实录。

## 3. 内容单元拆分

重新读取《访谈实录》，按连续语义拆分内容单元。一个单元通常包含一个主张或一组紧密相关的信息。

不要按固定字数机械切分。以下情况通常应新建单元：

- 主题明显转换
- 出现新的独立判断
- 从判断转向新的数据、案例或反例
- 受访者补充先前遗漏的条件或修正先前说法
- 另一位受访者给出不同口径

每个单元记录来源时间戳或行号，确保能重新找到原文。

## 4. 覆盖矩阵格式

写入 `纪要覆盖矩阵_{主要受访者姓名}_{YYYYMMDD}.json`：

```json
{
  "version": 1,
  "content_units": [
    {
      "id": "U001",
      "source_ranges": ["访谈实录第18-26行"],
      "summary": "受访者说明产品验证周期及当前进展",
      "claims": [],
      "reasoning": [],
      "data": [],
      "cases": [],
      "premises": [],
      "limitations": [],
      "exceptions": [],
      "uncertainty": [],
      "question_id": null,
      "minutes_location": null,
      "status": "pending",
      "excluded_reason": null
    }
  ]
}
```

字段规则：

- 所有内容字段只记录原文实际出现的信息
- 原文没有的字段使用空数组，不推导、不补写
- `summary` 只作导航，生成纪要时必须回读原始片段
- 每个未排除单元只能有一个主要 `question_id`；可在摘要中注明与其他问题的关联
- `excluded_reason` 仅允许：寒暄、纯应和、流程话术、没有新增信息的重复表述

## 5. 提炼《有效问题》

有效问题是完整覆盖的组织骨架，不是追求最少数量的问题列表。

- 每个问题对应清晰且相对独立的主题
- 一个问题若需要承载多个独立结论，应拆分
- 连续追问只有在属于同一主题时才合并
- 访谈后半段重回旧主题时，将新内容映射回旧问题
- 所有未排除内容单元必须分配问题编号

生成后检查：是否存在 `question_id` 为空的未排除单元；若有，先补问题，不进入纪要阶段。

## 6. 逐问题生成《访谈纪要》

每次只处理一个问题：

1. 从覆盖矩阵找到该问题的全部内容单元。
2. 按 `source_ranges` 重新读取《访谈实录》的原始片段。
3. 用受访者口吻写出核心观点。
4. 按原文实际存在的信息继续展开。
5. 把答案立即追加到《访谈纪要》。
6. 记录该问题已写入，但暂不把内容单元标为 `covered`。

展开原则：

- 有论据或推理才写论据或推理
- 有数据或案例才写数据或案例
- 有前提、限制、例外或不确定性才写这些内容
- 没有某类内容时，不增加空标题、套话或模型推导
- 不强制所有回答使用相同段落结构
- 保留原文判断强度、否定、条件语气和相互矛盾的口径
- 信息密集时充分展开，不设置篇幅上限
- 信息较少时以覆盖原文为上限，不注水

## 7. 反向覆盖审计

纪要完成后，从内容单元出发反向检查，而不是只顺读纪要：

1. 找到内容单元对应的纪要问题和具体段落。
2. 对照原始实录检查观点及其支撑信息。
3. 完整覆盖则填写 `minutes_location` 并标记 `covered`。
4. 只覆盖部分则标记 `partial`，补写后复核。
5. 完全遗漏则标记 `missing`，补写后复核。

重点检查：

- 人名、公司名、产品名、技术名
- 金额、比例、时间、产能、销量、增速、市场份额和单位
- 案例、类比、反例及观点修正
- 因果关系是否被加强或弱化
- “可能”“暂时”“在某条件下”“不是”等限定、否定和不确定表达

不要因为原文缺少数据、案例、限制或例外而判定不完整。完整性的含义是保留已出现的信息，而不是填满模板。

## 8. 异常简略检查

比较《访谈纪要》正文与清理后受访者实质回答文本的中文字符量：

- 纪要低于约50%时，强制再做一轮覆盖矩阵检查
- 该比例不是硬性篇幅要求
- 如果原文存在大量重复，低比例仍可能合理，但必须由覆盖矩阵证明没有信息损失
- 禁止为了达到比例重复表达或增加原文没有的内容

使用 `scripts/check_minutes_coverage.py` 检查最终矩阵状态和篇幅异常。退出码 `1` 表示需要再次人工核对覆盖矩阵，不代表可以自动扩写；退出码 `2` 表示矩阵仍存在未解决状态或结构错误。

## 9. 断点恢复

- 无阶段文件：从输入读取开始
- 只有《访谈实录》：建立覆盖矩阵
- 有实录和覆盖矩阵：检查内容单元是否完整，再生成《有效问题》
- 有效问题已完成：从第一个未写入的问题继续生成纪要
- 纪要已生成：从第一个非 `covered` 内容单元开始反向审计
- 三份文件完整且矩阵无 `pending`、`partial`、`missing`：直接汇报

恢复时优先读取已落盘文件，不重新依赖更长的原始输入。
